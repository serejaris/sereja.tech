Задачи:

Как вести задачи для агентов

Задачи уже лежат файлами в папке отдела. Дальше вопросы: когда их переносить, куда и как агенту самому брать следующую. Гайд отвечает на те, что чаще всего звучат в моих потоках.

8 октября 2026 · гайд обновляется

Задачи для агентов я сначала держал в файлах, потом в GitHub, а теперь держу в графе задач. Переезжал каждый раз по одной причине: старое место переставало держать работу. Файлы не видели агенты из других папок. GitHub перестал выдерживать команду агентов, которая работает круглые сутки. Из моей системы здесь только то, о чём спрашивают студенты моих потоков. Я собрал больше сотни таких вопросов, и повторяются они почти дословно.

Гайд для тех, у кого задачи уже лежат файлами в папке отдела: по файлу на задачу, со статусом и следующим шагом. GitHub вы открывали разве что по ссылке. Команд здесь почти нет, объяснений много. Вы унесёте правило, где живёт задача, и признаки, что пора на следующую ступень. А ещё промпт, который переносит задачи в GitHub за один заход.

Слова, которые встретятся дальше:

01

Где живёт задача?

Это самый частый вопрос во всех потоках. Задачи лежат в штабе или в каждом проекте? Почему статус в штабе один, а в проекте другой?

Правило такое: задача живёт в отделе, который отвечает за её результат. Письмо клиенту живёт в отделе продаж. Конспект урока живёт в отделе обучения.

Штаб: это папка с правилами, где агент узнаёт всё про мою работу. Задачи штаб у себя не хранит. В его правилах по строке на каждый отдел: где лежат задачи этого отдела. По этим строкам агент утром собирает дела из всех отделов в один список.

Есть третий вид папки: сайт, бот, учебная платформа. Туда сдают работу. Своих задач там нет. Агент делает правку на сайте, а ссылка на правку возвращается в задачу отдела. Отличить отдел от такой папки помогает один вопрос: что пропадёт, если её завтра удалить. Пропал сайт, значит пропал продукт. Пропал отдел, значит пропала память о том, что делается и зачем.

Дубли появляются, когда одна задача записана в двух местах. Статус обновили в одном, а читают из другого. Лечится это одним источником: у задачи одно место, всё остальное на него ссылается. Доска, сводка дня и отчёт только показывают задачу. При переезде старый файл остаётся и становится указателем: «задача переехала, вот ссылка».

Раньше времени новая ступень добавит настройку и не добавит порядка. На маленькой работе один агент с хорошей задачей обгоняет любую систему

Названия в GitHub путают, но для задач хватит трёх: репозиторий, issues и доска. Ветки и слияния нужны для правок кода, это другая тема.

Обязательно ли GitHub?

Нет. Подойдёт любой сервис, который хранит задачи вне вашего компьютера: Notion, Linear, Trello, Яндекс Трекер, Битрикс. Если компания уже живёт в Linear, оставайтесь в Linear. Формат задачи переедет, если поменять пару строк в скилле. В инструменты я советую не влюбляться.

Я выбрал GitHub по трём причинам. Он бесплатный. Задачи лежат рядом с файлами отдела, которые и так там хранятся. Агенты умеют с ним работать без настройки, а ChatGPT после разового подключения видит задачи с телефона. Ограничение одно: у GitHub есть лимиты на число запросов. Человеку с парой агентов их обычно хватает. Команде агентов, которая работает круглые сутки, уже нет.

03

Как дробить работу на задачи?

Это второй по частоте вопрос. Задачи выходят то слишком общими, то слишком мелкими.

Начните с проверки. Задача: это работа, результат которой можно проверить. Если проверку не сформулировать, это мелкая правка. Её агент делает сразу, без задачи.

В хорошей задаче четыре вещи. Заголовок начинается с глагола: «Отправить клиенту письмо с итогами встречи». Один ответственный: «все вместе» значит никто. Признак готовности, который видно глазами: «письмо ушло, в нём три договорённости со встречи». И ссылка на результат, которая появляется при закрытии.

Если шаг нельзя проверить, режьте его ещё раз. Если первый этап большого проекта не даётся за неделю, он слишком велик. Большая работа становится эпиком, части становятся подзадачами.

Мельчить тоже не надо. Модель тянет задачу целиком, если дать её целиком. Дробят ради вашего контроля: где посмотреть результат и где передать работу другому агенту. Двадцать мелких шагов внутри одной задачи агент разложит сам.

Подробная карточка с контекстом и критериями кажется тяжёлой. Так и есть: такая подробность нужна агенту. Поэтому заводит и заполняет карточку агент, вы проверяете результат.

У каждой задачи четыре поля: заголовок с глаголом, кто ведёт, признак готовности, куда ляжет результат.

Если шаг нельзя проверить, разбей его ещё раз. Мелкие правки без проверки задачами не делай.

Свяжи все задачи с одним эпиком. Покажи мне список до того, как что-то создавать.
04

Как агент берёт задачу и не теряет её?

Агент ничего не помнит между разговорами. Он знает только то, что записано в задаче. Поэтому всё держится на двух моментах: в начале агент читает задачу, в конце записывает в неё.

Начало. Проще всего назвать задачу: «возьми задачу про письмо клиенту» или номер issue. Можно и без названия: агент сам смотрит открытые задачи отдела и берёт верхнюю по приоритету. Приоритеты вы пишете в правилах отдела.

Конец. Прежде чем закрыть разговор, агент записывает в задачу, что сделано, где остановились и какой следующий шаг. У меня это делает скилл manager, он подробно разобран в гайде «Как агент ведёт мои дела». Новый разговор открывает задачу и продолжает с того же места. Из другой папки, с другой моделью, хоть с телефона.

Статусы расходятся, когда запись пропускают. Правило: если агент не записал в задачу, этого не было. В чате «готово», в задаче пусто, значит не сделано. Сам по себе агент ничего не записывает, поэтому запись стоит в конце каждого разговора. Задача закрывается только со ссылкой на результат.

Новые задачи агент тоже заводит сам. У меня в правилах написано: любое обещание из разговора сразу становится задачей с номером. Так исчезают «мы вроде договаривались».

05

Что делать, когда задач сотни?

У студентов очередь дорастала до сотни, двухсот и четырёхсот задач. Все выглядят одинаково важными, и агент присылает весь список.

Утром я спрашиваю агента «что у меня на сегодня». Он собирает короткий список по приоритетам из правил: что горит и что ждёт моего решения. Остальное ниже, одной строкой. Саму очередь я глазами не читаю и доску почти не открываю.

Порядок в длинной очереди держат три вещи. Каждая задача висит под эпиком, поэтому четыреста задач читаются как десяток целей. В правилах написано, что важнее: у меня это деньги, люди и публикации. Раз в неделю скилл retro разбирает неделю и спрашивает, что из застрявшего снять, упростить или продолжить.

Сроки ставьте для себя и людей вокруг. Агент сроков не чувствует: для него задача либо готова к работе, либо чего-то ждёт.

06

Зачем граф, если есть GitHub?

9 сентября моя команда агентов перестала вести задачи в GitHub. Агенты заводят и разбирают задачи круглые сутки, и GitHub перестал выдерживать этот поток запросов. 2 октября я записал решение: задачи живут в графе, GitHub остаётся витриной.

Граф задач: это база, где у задачи кроме статуса есть связи. «Письмо клиенту» ждёт задачу «Расшифровать встречу». Пока встреча не расшифрована, письмо не готово к работе. Агент спрашивает граф, что готово, и получает задачи, у которых всё нужное уже сделано. Бид: это одна задача в таком графе. Сам инструмент называется beads, он бесплатный и с открытым кодом.

У каждого отдела свой граф. Штаб собирает сводный вид всех графов, эту часть я сейчас достраиваю. В GitHub уходят только важные эпики: про неделю, деньги, людей и публикации. Работа идёт в графе. В GitHub я смотрю общую картину.

Нужен ли граф вам сейчас? Скорее нет. Он окупается, когда задачи заводят и разбирают агенты, а вы только принимаете работу. Начните с GitHub. Правило «задача живёт в отделе» переживёт и следующий переезд: в графе оно то же самое.

07

Как перейти с файлов на GitHub

  1. Заведите репозиторий для отдела. Попросите агента: «Опубликуй эту папку в приватный репозиторий на моём GitHub».
  2. Перенесите открытые задачи. Промпт ниже делает из каждой открытой задачи issue, а старые файлы превращает в указатели.
  3. Запишите в правила отдела, где живут задачи. Задачи живут в issues этого репозитория, новые заводятся там же. Промпт делает и это.
  4. Соберите доску, если отделов больше одного. Попросите агента завести одну доску в GitHub Projects и добавить в неё открытые задачи всех отделов.
  5. Проверьте в новом разговоре. Спросите агента «что у меня на сегодня». Ответил по issues, значит переезд закончен.
Промпт агенту · перенести задачи в GitHub Issues
Перенеси открытые задачи этого отдела в GitHub Issues текущего репозитория.

Прочитай AGENTS.md и все файлы в tasks/, кроме шаблона. Открытыми считай задачи со статусом «новая», «в работе», «на приёмке» или «заблокирована». Закрытые не переноси.

Для каждой открытой задачи создай одну issue. Сохрани результат, состояние, контекст, решения, следующий шаг и ссылку на результат.

Старые файлы не удаляй. Преврати каждый в указатель: ссылка на issue и пометка, что состояние здесь больше не обновляется.

Допиши в AGENTS.md правило: открытые задачи отдела живут в issues этого репозитория; новая задача заводится там же; перед работой агент читает issue и комментарии, после работы записывает состояние и следующий шаг; задача закрывается со ссылкой на результат.

Проверь, что второго места для задач не осталось. Верни таблицу «файл → issue».
08

Какие принципы работают везде

Файлы, GitHub или граф: эти правила не меняются при переезде и работают для любой задачи, которую вы отдаёте агенту.

У задачи одно место

Всё остальное ссылается на это место: доска, сводка дня, отчёт. Второе место для той же задачи рано или поздно разойдётся с первым.

Как с семейным календарём: стоит завести второй, и кто-нибудь пропустит дантиста.

Нет записи, значит нет работы

Агент знает только то, что записано в задаче. Сказанное в чате исчезает вместе с закрытой вкладкой.

Как на стройке: сделано то, что прораб записал в журнал работ.

Задачу закрывает ссылка

Задача закрывается ссылкой на результат: файл, пост, отправленное письмо. Слово «готово» без ссылки ничего не закрывает.

Как с курьером: заказ закрыт, когда есть фото пакета у двери.

У каждой задачи есть родитель

Каждая задача висит под целью. Тогда сотня задач читается как пять целей, и видно, зачем нужна каждая.

Как чек в папке расходов: без папки через месяц не вспомнить, за что платили.

Выше по ступени, когда нынешняя мешает

Новое место для задач добавляет настройку и привычки. Переезжайте, когда старое место перестало держать работу.

Как со складом: его не арендуют под одну коробку.

09

Коротко о частых вопросах

Контекст задачи хранится в issue?

Да. Описание и комментарии: это и есть память задачи. Следующий разговор читает их и продолжает с того же места.

Нужен ли GitHub отделу, где тексты и картинки?

Не обязательно. Если работа отдела живёт в другом сервисе, задачи можно держать там же. Важнее, чтобы место было одно.

Как смотреть задачи с телефона?

Подключите GitHub к ChatGPT. После разовой настройки он отвечает «что у меня на сегодня» по вашим issues.

Заводить задачу задним числом, если работа уже сделана?

Да. Заведите её под нужным эпиком и сразу закройте ссылкой на результат. Так работа не выпадет из картины недели.

Скилл manager запускать в каждом разговоре или только в штабе?

В конце каждого разговора, где двигалась задача, в папке её отдела. Штаб сам задач не хранит, ему записывать нечего.

Пока писался этот гайд, мой собственный manager ещё записывал состояние в GitHub, хотя задачи уже переехали в граф. Его перевод на граф стоит у меня отдельной задачей, с эпиком и ссылкой. Решение о переезде записывается за один день. Скиллы и привычки догоняют его по одному, и гайд будет обновляться вместе с ними.
