Приложение становится видимым для владельца, когда ключевые действия пишутся событиями: открытие карточки, клик по разделу, signup. События складываются в self-hosted аналитику, и читать эту базу может и человек, и агент. Ниже разбор двух стеков, Umami и PostHog, моя пятерка событий для доски редакционного отдела и промпт агенту, с которого начинается подключение. Весь путь занимает один вечер.

## События это зрение приложения

Доска моего редакционного отдела собирается как обычное приложение: React, shadcn, фид board-feed.json. Открыть её можно из любого места. При этом на вопрос "что люди открывают и где застревает приёмка" доска пока отвечает плохо: событий у неё ещё нет, пятерка из этой статьи написана заранее.

Событие это строчка в базе: имя, поверхность, время. Написал её в self-hosted аналитику, и приложение стало наблюдаемым. PostHog формулирует принцип прямо: видимость в то, что делают пользователи, плюс контроль над тем, где живут данные. Обе половинки важны. Видимость без владения данными означает отдать поведение своего приложения чужой площадке.

Статистику моего Telegram канала я уже читаю из собственной базы: сырые данные ходят через телетон, как устроен такой путь, разбираю в статье про [Telegram API вместо JSON экспорта](/blog/telegram-api-vs-json-export/). Агенты научились читать такие базы как обычный источник данных. Аналитика из отчёта превращается в интерфейс приложения.

## Umami и PostHog: сравнение под задачу

Оба инструмента open source и ставятся на собственный сервер. Развилка между ними это развилка между простотой и полнотой платформы, и решает её задача.

[Umami](https://umami.is) это простой веб-аналитик под лицензией MIT, работает на PostgreSQL, без cookies.

Гайд PostHog ["8 best open source analytics tools you can self-host"](https://posthog.com/blog/best-open-source-analytics-tools) (обновлён 09.03.2026) описывает его позицию честно: privacy-first, базовая веб-аналитика, easy to self host, no cookies.

Третья версия Umami добавила session replay и heatmap и попрощалась с MySQL: теперь нужны Node 18.18+ и Postgres, код живёт в репозитории [umami-software/umami](https://github.com/umami-software/umami). Минус из гайда один: Postgres масштабируется хуже ClickHouse. Для приложения с человеческим трафиком это различие остаётся теорией.

PostHog это all-in-one платформа: аналитика, флаги, эксперименты, реплеи в одном флаконе. Плата за полноту: тяжелее деплой и больше движущихся частей.

Совет коллеги Andre Shmelkov (диалоги 29.04 и 11.08.2026) звучал так: "мега советую umami.is", "просто деплоишь на Vercel", "трекать события ключевые, чтобы конверсии мерять", "вся аналитика в удобной БД для агентов". Совет дельный, и решение по своей доске я всё-таки оставил открытым: события придуманы заранее и переживут любой выбор стека.

## Пять событий доски

Задача вечера звучит так: придумать пять событий своего приложения. Моя пятерка для доски редакционного отдела.

1. **signup**: человек первый раз открыл доску и представился системе.
2. **section_open**: клик по разделу. Видно, какой раздел живой, какой пустует.
3. **card_open**: открытие карточки приёмки, главной рабочей единицы.
4. **card_open_no_action**: открыл карточку и ушёл без действия. Так ловится застревание приёмки.
5. **feed_fetch**: запрос фида board-feed.json. Машины тоже читатели, это события агентов.

Пяти событий хватает для первого вечера. Каждое отвечает на вопрос владельца, который раньше висел в воздухе. Имена я держу машинными: section_open агент читает лучше, чем "клик по разделу".

## Вечер подключения

Дальше работа агента. Промпт, с которого начну инструментирование доски, и который подходит любому приложению со своим списком событий.

{{< callout prompt >}}
Мы выбираем self-hosted аналитику для нашего приложения. Сравни Umami и PostHog под нашу задачу: данные у нас, без cookies, минимум движущихся частей, деплой на Vercel с базой PostgreSQL. Предложи один вариант и обоснуй. Потом подключи трекинг пяти событий: signup, section_open, card_open, card_open_no_action, feed_fetch. Пропиши вызовы в коде, проверь, что события видны в дашборде, и выведи в терминал пять строк: имя события и счёт за сегодня.
{{< /callout >}}

Что делает агент: сравнит стеки, поднимет выбранный, внесёт трекер, обернёт пять вызовов, проверит приём событий. Моё участие: придумать пятерку и посмотреть на дашборд. Один вечер с запасом.

Грабли известные, из документации: в дев-сборке события молчат и приходят только из продакшн-сборки; домен в настройке аналитики записан с www, а приходит без; часть счётчиков прячется за adblock. Проверка одна: событие видно в дашборде в течение минуты после клика.

## Аналитика как интерфейс

Ниша self-hosted аналитики устоялась: у каждого инструмента ясная роль, стоимость ошибки выбора упала. Событие пишется с той поверхности, где живёт пользователь. Шмельков добавлял: "аналитика из любого места: веб, бот, хоть ютуб канал". База телетона уже держит статистику канала, веб-часть закроет выбранная аналитика, и обе дороги сходятся в одном месте: в базе, куда агенты ходят за ответами.

Разделы приложения собираются из событий: дашборд владельца это те же пять событий, свёрнутые в ответ. Утренний вопрос "где застряла приёмка за неделю" превращается в запрос агента к базе аналитики, ответ приходит цифрами. Один источник для человека и для машины.

## Частые вопросы

### Postgres протянет?

Для приложения с человеческим трафиком: да. События такого приложения это тысячи строк в день, Postgres переживает поток без настройки. Разница с ClickHouse становится заметной на миллионах событий в день, там сильнее PostHog.

### А если понадобится session replay?

В третьей версии Umami session replay и heatmap уже есть. Упрётесь в потолок платформы, PostHog рядом: пять событий просто переезжают с вами.

### Что с приватностью посетителей?

Umami работает без cookies, данные живут на вашем сервере. Ретеншен и правила хранения всё равно стоит решить до подключения, это открытый вопрос моего сетапа.
