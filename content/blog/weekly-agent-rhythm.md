Агенты ускоряют исполнение задач в десять раз, но без жесткого недельного ритма они лишь с удесятеренной скоростью производят энтропию. Мой рабочий ритм строится на трех опорах: автоматический сбор фактов из Git, календаря и тикетов для честной ретроспективы, превращение повторяющихся ошибок в правила AGENTS.md и формулирование плана недели через проверяемые результаты вида «К пятнице верно, что X». Этот цикл превращает хаотичные диалоги с моделями в предсказуемую производственную систему.

## Недельный ритм с агентами: ранний вердикт

Работа с автономными моделями создает обманчивое ощущение безграничной продуктивности. Когда терминал за пару минут генерирует рабочий сервис, легко потерять связь между затраченным временем и реальной ценностью для бизнеса.

Главный вывод из сотен агентских сессий: моделям нельзя делегировать выбор направления без внешнего контура контроля. Агент отлично пишет код, находит баги, собирает интеграции и перекладывает данные между базами. Ответственность за фокус, отбор задач и отсечение лишнего всегда остается на человеке.

Недельный ритм решает главную проблему соло-разработчика: он убирает самообман. Вместо субъективных ощущений «я всю неделю усердно трудился» система опирается на твердые артефакты. Каждое воскресенье агент сканирует закрытые задачи, коммиты и встречи, сверяет их с обещаниями понедельника и проводит жесткое интервью. Ошибки немедленно упаковываются в правила для `AGENTS.md` и кастомные скиллы. Понедельник начинается с формулировки трех-четырех ключевых результатов недели. Дни наполняются задачами из единой очереди GitHub Projects через короткие утренние файлы фокуса. Как я сформулировал в [манифесте личной корпорации](/blog/lichnaya-korporatsiya/), главный враг системы: отдел, который построили и забыли. Лечится это именно расписанием и недельным ретро.

## Когда неделя растворяется в сотне чатов

Типичная неделя активного пользователя Claude Code или Codex CLI начинается с энтузиазмом. В понедельник утром появляется свежая идея: переписать авторизацию, добавить векторный поиск, собрать новый дашборд или поэкспериментировать со свежей моделью.

К среде в терминале открыто двадцать вкладок. В каждой вкладке агент решает локальную задачу: оптимизирует SQL-запросы, генерирует компоненты интерфейса, настраивает пайплайн деплоя. Работа кипит, контекст горит, коммиты исчисляются десятками. Возникает стойкое чувство триумфа: за пару дней сделан объем, на который раньше уходили месяцы работы целой команды.

В пятницу вечером наступает момент отрезвления. Открываешь список проектов и понимаешь: ключевой продукт, приносящий выручку, не сдвинулся ни на миллиметр. Важная для клиентов интеграция осталась в статусе черновика. Зато появился внутренний микросервис для генерации красивых графиков, который никто не просил.

Один из моих знакомых точно сформулировал эту ловушку: «ты ничего не заработал, но зато сделал 10 проектов, которые никто не просил». Агентская гиперактивность коварна. Модель охотно соглашается с любым новым импульсом, мгновенно разворачивает архитектуру и увлекает разработчика в бесконечные технические дебри.

Причина этого сценария заключается в отсутствии границы между стратегическим решением и локальным исполнением. Когда оперативное планирование происходит прямо внутри диалоговой сессии, контекст задачи размывается. Человек поддается соблазну решить сиюминутную проблему, забывая про недельные обязательства. Если запустить сотню субагентов без четкой цели, получается только [организованный шум и сожженные токены](/blog/orchestration-without-goals/).

Чтобы разорвать этот круг, требуется внешний операционный маховик. Агент становится беспристрастным аудитором, фиксирующим расхождения между декларациями и реальностью.

## Операционный цикл недели: пять фаз одного маховика

Устойчивая работа с персональной агентской корпорацией требует замкнутого контура управления. Мой процесс состоит из пяти взаимосвязанных фаз, которые сменяют друг друга каждую неделю.

1. **Ретроспектива (воскресенье):** агент собирает факты из внешних источников, формирует scorecard выполнения обещаний, проводит интервью по сложным задачам и триажит открытые тикеты.
2. **Планирование (понедельник):** формулирование трех ключевых outcomes недели через формулу «К пятнице верно, что X», распределение задач по матрице делегирования и привязка к квартальным целям.
3. **Ежедневный фокус (со вторника по четверг):** десятиминутная утренняя сверка, генерация файла дня, выбор задач из единого бэклога без переключения на фоновый шум.
4. **Агентское исполнение:** запуск автономных сессий в Claude Code и Codex CLI по четким спецификациям с фиксацией промежуточных результатов в PR и issue comments.
5. **Упаковка опыта:** анализ сбоев сессий, обновление инструкций в AGENTS.md и создание специализированных скиллов под повторяющиеся операции.

Ядром всей системы выступает связка GitHub Projects и Штаба правил. Все задачи живут в одном месте, как описано в статье [«Из вайбкодера в CEO»](/blog/vibecoder-to-ceo-personal-corp-github/), а накопленный опыт становится законом для последующих сессий.

Для поддержания ясности в проекте критически важно строго разделять три информационных экрана:

- **Локальный файл dashboard.html в репозитории HQ:** оперативный экран состояния системы, отображающий статус работающих демонов, состояние локальных баз данных, актуальные порты и здоровье инфраструктуры.
- **Единая очередь в GitHub Projects:** стратегический канбан-бэклог всех репозиториев, где задачи отсортированы по приоритету, статусу исполнения и закрепленным исполнителям. Как организовать [контекст проекта в GitHub Issues](/blog/github-issues-project-context/), я разбирал отдельно: issue служит строгим контрактом с критериями приёмки.
- **Аналитический HTML weekly report:** итоговый документ ретроспективы, фиксирующий срез недели, процент выполнения обязательств и список обновленных правил.

Такое разделение исключает путаницу между тем, что запущено прямо сейчас, тем, что стоит в очереди на разработку, и тем, какие выводы сделаны по итогам прошедших дней.

## Анатомия ретро: от фактов в Git до честного интервью

Человеческая память ненадежна. В конце сложной недели мы склонны помнить лишь последние яркие инциденты или испытывать необоснованное чувство вины за несделанное. Ретроспектива с агентом исключает эмоциональные искажения, потому что опирается исключительно на факты.

Процесс ретроспективы занимает двадцать пять минут и состоит из четырех шагов.

### Шаг 1. Автоматический сбор фактов

Я прошу агента просканировать все источники данных за последние семь дней. Агент запускает скрипты сбора и формирует сырую ведомость недели.

В эту ведомость входят:
- Список коммитов и созданных pull requests во всех рабочих репозиториях.
- Список созданных, обновленных и закрытых issues в GitHub Projects.
- Календарные события, проведенные созвоны и записи транскриптов из Granola.
- Логи потребления токенов и количество запущенных сессий в терминале.

Результатом работы становится хронологическая таблица: что реально происходило каждый день с понедельника по воскресенье.

### Шаг 2. Scorecard обещаний

Агент открывает файл плана, составленный в прошлый понедельник, и сопоставляет каждый пункт с собранными фактами.

Для каждого запланированного результата выставляется один из трех статусов:
- **Выполнено:** есть ссылка на закрытый PR, работающий сервис или опубликованный материал.
- **Сдвинуто:** работа начата, есть промежуточные коммиты, но итоговый критерий готовности не достигнут.
- **Провалено:** задача даже не бралась в работу либо закрыта без результата.

Агент вычисляет процент выполнения недели. Если выполнено меньше семидесяти процентов запланированного объема, агент блокирует переход к новому планированию до выяснения причин перегрузки.

### Шаг 3. Сократическое интервью недели

Это ключевой этап ретроспективы. Агент переходит в режим строгого интервьюера и последовательно задает прямые вопросы по проблемным зонам недели.

Диалог строится вокруг трех обязательных тем:

1. **Вопрос о целесообразности:** «Ты провел шесть часов за оптимизацией парсера логов. Зачем ты делал эту задачу, если она отсутствовала в плане понедельника?»
2. **Вопрос о расхождениях в оценке:** «Почему создание посадочной страницы заняло три дня вместо запланированных двух часов? Где именно агент застрял и почему сессия не была сброшена вовремя?»
3. **Вопрос о блокировках:** «Какой инвариант процесса был нарушен, из-за чего сломался автоматический деплой в среду вечером?»

В процессе ответов на эти вопросы быстро вскрываются паттерны прокрастинации: уход в полировку второстепенного кода, избыточное усложнение архитектуры или попытки спасти тупиковую сессию вместо ее перезапуска.

### Шаг 4. Triage задач в ноль

После завершения интервью агент открывает бэклог в GitHub Projects и проводит полную инвентаризацию:

- Закрывает задачи, потерявшие актуальность за прошедшую неделю.
- Декомпозирует слишком крупные тикеты, висящие без движения дольше двух недель.
- Формирует чистый пул задач, готовых к взятию в следующий спринт.

{{< callout type="insight" >}}
Проведи еженедельную ретроспективу по фактам за последние 7 дней.
1. Собери список коммитов и закрытых PR по всем репозиториям через gh cli.
2. Сверь факты с планом из файла weekly-plan.md и заполни scorecard выполнения.
3. Задай мне по очереди 3 жестких вопроса по задачам, которые заняли больше всего времени или не были запланированы.
4. Сформулируй 2 правила для добавления в AGENTS.md на основе найденных сбоев.

## Планирование недели: формулируем результаты вместо бесконечного списка

Большинство списков задач страдают фундаментальным изъяном: они описывают бесконечные процессы вместо измеримых результатов. Формулировки вроде «поработать над ботом» или «исследовать векторные базы» создают иллюзию занятости, но не содержат критерия завершения.

В нашей системе действует жесткое правило: каждый пункт недельного плана формулируется как проверяемое утверждение: «К пятнице верно, что X».

Сравните два подхода:
- Процессная формулировка: «Заниматься интеграцией платежей в боте».
- Результативная формулировка: «К пятнице верно, что тестовый пользователь может нажать кнопку оплаты, получить ссылку, провести платеж и автоматически получить доступ к закрытому чату».

Вторая формулировка содержит однозначный критерий приемки. В воскресенье агенту достаточно выполнить один проверочный сценарий, чтобы подтвердить закрытие цели.

### Матрица делегирования для работы с моделями

При распределении задач на неделю я использую адаптированную матрицу Эйзенхауэра, разделяющую деятельность на две фундаментальные зоны.

Первая зона: **Суждения основателя**. Сюда входят задачи, требующие вкуса, эмпатии, высокоуровневого выбора стратегии и личного общения.
- Определение продуктового позиционирования.
- Выбор целевой аудитории и ценностного предложения.
- Архитектурные развилки с компромиссами по стоимости и сложности.
- Личные созвоны, интервью и преподавание.

Вторая зона: **Агентская автономия**. Задачи с четкими входными данными и детерминированными критериями успеха.
- Написание тестов и покрытие пограничных случаев.
- Верстка компонентов по готовым спецификациям.
- Настройка скриптов миграции данных.
- Автоматический сбор аналитики и подготовка отчетов через [агентов на расписании launchd](/blog/launchd-macos-agent-scheduler/).

Если задача попадает в зону агентской автономии, я не трачу на нее личное время в течение дня. Я формулирую спеку в issue, запускаю сессию и возвращаюсь только на этапе ревью готового pull request.

### Ежедневный фокус и файлы дней

Недельный план декомпозируется на файлы отдельных дней: например, `2026-08-24.md`. Утром я открываю терминал и прошу агента составить расписание дня на основе общего плана.

Файл дня содержит ровно три блока:
1. **Главный фокус дня:** один ключевой результат, без которого день считается непродуктивным.
2. **Очередь задач из GitHub Projects:** два-три конкретных номера issue для передачи агентам.
3. **Вечерний чеклист фактов:** список ссылок на коммиты и PR, которые должны появиться к концу дня.

1. Выбери из GitHub Projects 3 приоритетные задачи, ведущие к главным outcomes недели.
2. Раздели задачи на мои действия и автономные спеки для агентов.
3. Сформируй файл дня с четким списком критериев готовности к вечеру.

## Стартовый набор: правила и промпты для запуска

Главный парадокс работы с AI звучит так: «Настраиваешь агента, чтобы он настроил тебя». Модели становятся зеркалом вашей дисциплины. Если в инструкциях зафиксированы четкие рамки, агент берет на себя роль строгого проектного менеджера.

В основе операционной памяти лежит базовый закон: «повторилось дважды: делегируй». Если в процессе работы одна и та же ошибка возникает во второй раз, я не исправляю ее вручную. Я прошу агента сформулировать новое правило в AGENTS.md или упаковать повторяющийся сценарий в отдельный скилл.

### Архитектура файла AGENTS.md

Файл `AGENTS.md` в корне репозитория служит единым источником правды для любой модели, входящей в проект.

Его структура включает следующие разделы:
- **Назначение и границы репозитория:** за что отвечает данный проект и какие смежные сервисы он использует.
- **Канонические пути:** точное расположение конфигураций, исходного кода, тестов и документации.
- **Инварианты и запреты:** список абсолютных ограничений (например, запрет коммитить секреты, запрет менять схему базы без миграций, запрет использовать сторонние UI-библиотеки без согласования).
- **Команды валидации:** точные инструкции для проверки работоспособности перед созданием PR.

### Упаковка сценариев в скиллы

Когда цепочка действий состоит из нескольких вызовов инструментов, она оформляется как скилл в папке `.claude/skills/`.

Примеры работающих скиллов в моем сетапе:
- `weekly-retro`: автоматический сбор коммитов, подсчет scorecard и генерация отчета.
- `daily-focus`: утренняя сверка бэклога и создание файла дня.
- `triage-issues`: скрипт для пакетного закрытия устаревших тикетов и проверки тегов.

1. Выдели 2 повторяющихся сбоя в контексте или командах.

На момент проведения аудита в центральной доске GitHub Projects зафиксировано следующее состояние: 227 открытых задач за весь период, 97 успешно закрытых тикетов и 130 активных задач в бэклоге, распределенных по 23 репозиториям.

Управлять таким объемом в одиночку без команды менеджеров возможно только благодаря строгой типизации задач и жесткому недельному ритму.

Вот как выглядит распределение нагрузки в течение стандартной недели:

### Понедельник: запуск направлений

Утро начинается с ревизии 130 активных тикетов. Из них выбираются ровно пять задач, напрямую связанных с ключевыми целями месяца.

По каждой задаче агент создает подробную спецификацию прямо в теле issue:
- Контекст проблемы и текущее поведение системы.
- Ожидаемый результат в виде проверяемого поведения.
- Список файлов, подлежащих изменению.
- Команды для автоматической проверки.

### Со вторника по четверг: параллельные сессии

В течение недели я держу открытыми две-три сессии.

В Claude Code запускаются задачи средней сложности: верстка страниц, написание парсеров, создание новых эндпоинтов API. Модель получает ссылку на номер issue, считывает контекст из `AGENTS.md`, создает ветку, выполняет работу и запускает локальные тесты.

В Codex CLI уходят масштабные архитектурные переработки: рефакторинг работы с базой данных, оптимизация тяжелых очередей или написание комплексных интеграционных тестов.

Моя роль в эти дни сводится к проверке диффов: я смотрю на логи выполнения и результаты тестов, не погружаясь в ручное редактирование кода.

### Пятница: фиксация и аудит

В пятницу во второй половине дня новые сессии не запускаются. Это время подведения итогов:
- Мердж всех открытых pull requests, прошедших автоматические проверки.
- Деплой стабильных версий на продакшен-серверы.
- Запуск ретро-скрипта для фиксации итогов недели.

Из 15 запланированных на неделю микрозадач обычно закрывается 11-13. Оставшиеся тикеты либо переносятся с явным обоснованием, либо удаляются как не прошедшие проверку реальностью.

## Четыре поломки процесса и способы их починить

Даже самая продуманная система дает сбои под воздействием усталости или внешних факторов. За месяцы работы я выделил четыре типичные поломки процесса.

### Поломка 1. Иллюзия прогресса

**Симптом:** за неделю закрыто тридцать мелких тикетов, но ключевой проект не продвинулся. Вы чувствуете усталость, а бизнес-результат равен нулю.

**Причина:** выбор простых и приятных задач из бэклога вместо сложных и неопределенных вызовов.

**Лечение:** агент на ретроспективе задает жесткий вопрос: «Зачем ты делал эти задачи, если они не влияют на метрики?» В понедельник вводится ограничение: не больше трех ключевых задач в плане на неделю. Мелкие тикеты берутся только после закрытия главных outcomes.

### Поломка 2. Раздувание контекста и потеря правил

**Симптом:** к середине недели агент начинает забывать договоренности, ломает существующие тесты и переписывает код на свой лад.

**Причина:** слишком длинные диалоговые сессии с накоплением сотен сообщений и устаревшим файлом `CLAUDE.md`.

**Лечение:** внедрение правила двух сбоев. Если модель ошиблась дважды в одном контексте, сессия немедленно сбрасывается через `/clear`. Все долгосрочные правила выносятся из контекста чата в компактный модульный `AGENTS.md`.

### Поломка 3. Хаос в дашбордах

**Симптом:** задачи теряются между локальными заметками, вкладками браузера и сообщениями в мессенджере.

**Причина:** смешение оперативного статуса инфраструктуры и очереди задач.

**Лечение:** строгое разделение трех экранов. Все задачи живут только в GitHub Projects. Текущее состояние серверов отображается только в `dashboard.html`. Итоги недели фиксируются исключительно в еженедельном отчете. Любая мысль из мессенджера оформляется через агентский скрипт прямо в issue.

### Поломка 4. Зависание бэклога

**Симптом:** количество открытых тикетов переваливает за сотню, список превращается в кладбище несбывшихся надежд, вы перестаете в него заглядывать.

**Причина:** отсутствие регулярной чистки и страх удалить неактуальную идею.

**Лечение:** пятничный triage в ноль. Агент сканирует задачи без движения дольше четырнадцати дней и предлагает закрыть их с пометкой «отклонено по сроку давности». Если идея действительно важна, она вернется в процесс естественным путем.

## Чек-лист работающего цикла: критерии готовности

Проверьте ваш процесс по следующим критериям. Если хотя бы один пункт не выполняется, операционный маховик будет пробуксовывать.

### Блок ретроспективы
- [ ] Все факты недели собраны автоматически из Git, календаря и тикетов без ручного поиска.
- [ ] Заполнен scorecard выполнения плана с точным расчетом процента закрытых обязательств.
- [ ] Проведено интервью с разбором незапланированных задач и причин перегрузки.
- [ ] По итогам ретро в `AGENTS.md` добавлено минимум одно новое правило или инвариант.
- [ ] Проведен triage открытых тикетов в GitHub Projects, неактуальные задачи закрыты.

### Блок планирования
- [ ] Сформулировано от трех до пяти ключевых результатов в формате «К пятнице верно, что X».
- [ ] Задачи разделены по матрице делегирования на суждения основателя и агентскую автономию.
- [ ] Все агентские задачи имеют четкие критерии приемки и заведены в единую доску проектов.
- [ ] Календарь очищен от лишних встреч, заблокированы окна для глубокой работы.

### Блок ежедневного исполнения
- [ ] Каждое утро начинается с генерации файла дня и сверки с недельными целями.
- [ ] Агентские сессии запускаются по четким спецификациям из номеров issue.
- [ ] При двух последовательных ошибках сессия сбрасывается, а контекст обновляется.
- [ ] В конце дня зафиксированы ссылки на созданные коммиты и открытые PR.

## Ответы на частые вопросы и следующий шаг

### Сколько времени занимает ретро и планирование вместе с агентом?
При наличии настроенных скриптов весь процесс занимает не более сорока пяти минут в неделю. Сбор фактов и генерация scorecard занимают около пяти минут. Сократическое интервью длится пятнадцать-двадцать минут. Планирование следующей недели и генерация спецификаций для задач укладываются в двадцать минут.

### С чего начать, если у меня пока один проект и нет сложной инфраструктуры?
Начните с создания единого файла `AGENTS.md` в основном проекте и заведите простую канбан-доску в GitHub Projects. Разворачивать сразу двадцать три репозитория не требуется. В ближайшее воскресенье попросите Claude Code проанализировать коммиты за неделю и задать вам три вопроса по сделанной работе.

### Что делать, если модель на ретроспективе спорит или хвалит за все подряд?
По умолчанию языковые модели склонны к избыточной вежливости и похвале. Чтобы получить честный аудит, явно пропишите в промпте роль строгого внешнего консультанта: «Твоя задача: найти расхождения между планом и фактами, указать на неэффективно потраченное время и задать неудобные вопросы без комплиментов».

### Как перестать влезать в код руками во время агентских сессий?
Установите для себя жесткое психологическое ограничение: любые изменения вносятся только через промпт модели. Если агент написал неработающий компонент, опишите проблему словами и приложите логи ошибок. Это дисциплинирует мышление и учит формулировать точные технические требования.
