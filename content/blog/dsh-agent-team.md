Постоянная агентная команда живёт в файлах, а харнесс для неё сменная деталь. Моя редакция работает с 11 сентября и за один день переехала между тремя харнессами: утром Claude Code, днём omp внутри Cursor, вечером DeepSeek Harness. Переезд на сервер, дубли запусков и зависшее воплощение остановили работу минут на пятнадцать. Ниже анатомия: что именно лежит в репозитории, как команда поднимается одной строкой в чате и что происходит при рестарте.

## День, который обычно ломает команду

За 11 сентября в редакции случилось 29 наймов, всего в реестре треда 35 воплощений десяти ролей. В репозитории отдела за день ушло 56 коммитов, граф задач вырос до 54 бидов. Вечером тред переехал с Мака на сервер: граф задач заморозили на четверть часа, базу на новом месте сверили побайтно с исходником. 74 записи, 68 связей, 170 комментариев, все ключевые задачи на месте.

Дальше честный список поломок того дня. Работа первого такта осталась без коммитов и доехала только потому, что файлы уже лежали в дереве: единственная реальная потеря, и та по вине забытого коммита. Диспетчер дважды запустил одно и то же, лишние попытки остановили чисто. Одно воплощение зависло и молчало, архитектор его остановил, преемник довёл задачу до приёмки. В чужой коммит уехала правка README владельца, её вынули отдельным коммитом без переписывания истории. Симлинки скиллов лопнули при переезде, их восстановили отдельным прогоном после миграции.

Вывод из дня: харнесс меняется, модель меняется, работа продолжается, потому что состояние команды лежит в репозитории. Падает всё, что лежит только в памяти сессии.

## Где живёт команда

Состояние редакции это пять мест, и все они в репозитории:

- `settings.md` треда: пути, id эпика, команда сборки доски, монитор;
- `briefs/`: бриф на каждого агента, общая часть плюс роль;
- `state/`: реестр воплощений agents.json и архив канала channel.md;
- граф задач beads: база лежит прямо в репозитории, уезжает вместе с git push;
- доска владельца: html собирается из того же графа, живёт на localhost.

Ниже уровня файлов пусто. Правило одного места держит систему аккуратной: даты и пути в settings, кто что делает в графе, остальные места держат ссылку на канон. Дубль факта в двух файлах гарантирует расхождение через неделю.

Для владельца отдельная плоскость: доска собирается из того же графа задач. На ней приоритеты, блокеры и папка решений for-ris. Владелец смотрит одну страницу, агенты читают граф, расхождений между картинами мира нет.

DeepSeek Harness в этой схеме: агентный харнесс, где воплощения получают полный доступ к файлам, а транскрипты сессий пишутся в zstd-jsonl с метрикой totalTokens. Для команды это два следствия. Агентам можно работать по всем репозиториям отдела сразу. Монитор бюджета видит размер контекста каждого воплощения в моменте, без ожидания итоговых отчётов.

## Запуск с нуля

Три шага на старте:

```
bd init && bd doctor
BEADS_ACTOR=architect bd create "Редакционный отдел: цель" -t epic -p 0
/orchestrate
```

Первая команда поднимает граф задач и проверяет его здоровье. Вторая создаёт эпик, под которым висят все задачи треда, агент выполняет её сам. Третья это запись в чате: скилл оркестрации находит тред по репозиторию, читает состояние и поднимает продюсера, доску и монитор. При первом запуске, когда треда ещё нет, скилл создаёт его по шаблонам: settings, брифы, state.

Бриф роли стоит двух минут при найме и экономит час при работе: в нём границы агента, формат результата и правила следов. Найм в этой системе тоже запись в граф задач. Вот настоящий запрос найма из моего треда на этой неделе:

{{< callout prompt >}}
[найм-запрос] producer → architect: editor, переписка двух статей блога по правилам владельца (corp-content-ff8.107). Бюджет 400000, срочность P1
{{< /callout >}}

Архитектор по такому запросу создаёт свежее воплощение роли с брифом в руках. Дальше команда работает сама: продюсер ведёт такты, агенты берут задачи из графа, приёмка идёт по метке needs-review. После каждого записанного файла и пройденного теста агент оставляет комментарий в биде. К концу дня по одним комментариям видно, кто что сделал и на чём споткнулся.

Мой вход это решения на стыках: утвердить тему, принять или вернуть пакет. Плюс один вопрос в конце сессии, который окупается чаще любого ревью: какие проблемы заметил, что добавить в правила.

## Рестарт за минуту

Сессия умерла, контекст сгорел, это штатная ситуация. Восстановление занимает три действия: остановить зависшее воплощение, прогнать скрипт плана, запустить преемников.

```
python3 ~/Documents/GitHub/corp-ai/skills/orchestrate/scripts/restart_plan.py /path/to/repo
```

Скрипт одним прогоном собирает план из settings, реестра воплощений и resume.json: печатает бид такта и готовые запросы найма, с флагом `--apply` сам создаёт бид в графе. По опыту того дня подъём после смерти сессии занимает меньше минуты, причём рестарт случался и при переезде между харнессами.

## Монитор и ревью: чтобы команда не сгорала

Монитор бюджета читает транскрипты сессий и следит за максимальным размером контекста каждого воплощения. Порог предупреждения и порог алерта заданы в settings, универсальный бюджет сейчас 400 тысяч токенов. На DSH транскрипты лежат в zstd-jsonl, метрика это поле totalTokens. На среднем харнессе того дня монитор потерялся: транскриптов субагентов в записанной папке не оказалось, контроль сжался до итоговых отчётов. Это тоже аргумент за файлы: приборная панель живёт там же, где команда.

Ревью эффективности проходит после каждого завершённого воплощения: токены сверяются с внешними следами работы. След это комментарий в биде, коммит или файл. Работа без следа считается несделанной, сколько бы токенов в неё ни влезло. Возврат ревью один: правка в бриф роли, которую применяет архитектор при следующем найме. Бюджет превращается из абстрактной экономии в правило найма: пакет задач подгоняется под окно контекста, окно под роль.

## Грабли

Пять вещей, которые я бы записал в правила заранее:

1. Поиск по всему репозиторию без `--exclude-dir=.beads` вытащил 39 КБ бинарного мусора из embeddeddolt, четверть байтов ответа одного тика ушла на чтение этой ерунды.
2. Переменные окружения не живут между вызовами агента. Атрибуция в графе ставится префиксом в той же строке: `BEADS_ACTOR=editor bd comment ...`, иначе запись подписывается владельцем.
3. Идентификатор сессии в выводе инструмента валит вызов ошибкой формы ответа. Временные пути в выводе подставляются маской.
4. Симлинки `.claude/skills` лопаются при переезде машины, их восстановление это пункт чеклиста миграции, заранее, без ночных импровизаций.
5. Дефолтная модель найма проверяется на первом же запуске: в тот день часть воплощений нанялась агентом харнесса по умолчанию вместо ролевого, реестр правили руками.

## Итог

Агентная команда это файлы в репозитории, чат лишь одноразовое окно в неё. Когда состояние в git, смена харнесса стоит одного прогона скрипта, смерть сессии стоит минуты, а потерять работу можно ровно одним способом: забыть закоммитить.

Оркестрацию я пробовал и другими способами: [Symphony от OpenAI раздаёт задачи Codex через Linear](/blog/symphony-codex-orchestrator), это чужой демон для той же задачи. А [рой агентов для вёрстки](/blog/agent-swarm-frontend) показывает обратный конец: как выглядит работа субагентов, когда контракты уже раздали.
